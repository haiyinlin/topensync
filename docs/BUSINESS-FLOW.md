# TopenSync 业务流程

> 面向维护者与二次开发者。读完这一篇就能理解「一个文件从本地到远端，会经过哪些判断、在哪里被拦下、失败后怎么恢复」。

---

## 一、程序在做什么

**一句话**：把指定的本地文件夹单向同步到自部署 OpenList 暴露的夸克网盘存储，远端保持原始文件树，可直接浏览预览。

```
本地同步目录 ──(chokidar 监听)──▶ Planner ──▶ Transfer ──▶ OpenList ──▶ 夸克网盘
                    ▲                            │
                    │                            ▼
              SQLite 清单 ◀── Reconciler ◀──(定时/手动列举远端树)
```

三个不可协商的前提：

| 前提 | 含义 | 推论 |
|---|---|---|
| **单向** | 本地为准，远端不回传覆盖本地 | 对账只做校正，不做双向合并 |
| **不打包** | 小文件逐个直传 | 远端可直接浏览，不产生 zip/tar |
| **不绕过服务端** | 全部走 OpenList 标准 HTTP 接口 | 能用任何 OpenList 实例，不绑定夸克 |

### 启动后默认不开始

程序打开后**不开始**同步：本地扫描、远端对账、上传队列都要用户点顶栏的「开始同步」才启动。

为什么：备份工具多半开机自启，用户可能只是路过看一眼状态。启动瞬间就扫全盘、列远端树、抢带宽，不是用户想要的。

手动点「扫描本地」「对账远端」等价于开始同步——用户的显式动作优先。

**「还没开始」和「中途暂停」是两回事**，界面文案不同（开始同步 / 继续同步）。

## 二、两条扫描通道

这是整个程序最核心的概念。两者角色不同、不可互相替代。

| | 本地扫描（Watcher） | 远端对账（Reconciler） |
|---|---|---|
| 性质 | **变更事件源** | **对账基准** |
| 触发 | chokidar 实时 | 定时（默认 6 小时）+ 手动 |
| 覆盖 | 本地同步根目录 | 远端根目录 |
| 发现 | 「本地改了」 | 「远端被外部删了 / 改了 / 多了」 |
| 动作 | 直接进上传队列 | 产出差异 → 差异回流进同一个上传队列 |

**为什么必须有远端对账**

只扫本地有一个静默漏洞：你在 OpenList 网页端删了某个文件，本地 mtime 没变，清单就认为它已同步，于是永远不再上传，备份就此缺失。对账周期性地重列远端树来发现这类偏差。

**两条通道怎么不打架**

手动点「立即对账」时，若上传队列还没跑完，对账会**等它排空**再开始。否则清单里还没记上刚传完的文件，对账会把它们误判成「仅远端存在」——那是假差异，照着界面提示去处理反而会误删远端文件。

## 三、一个文件的上传决策链

文件进入上传队列后，依次经过四道闸门。**顺序不可调换**——每一道都在为下一道省流量或保证正确性。

### L1 快筛：内容没变，完全不上传

- **判据**：清单里的「上次成功同步时 size + mtime」与当前一致（1ms 容差）
- **命中**：整条链路结束，零上行流量
- **这是省用户上行流量的主力**

### 超限拦截：夸克单文件上限

- **判据**：文件大小 > `quarkMaxFileBytes`（默认 20GB）
- **命中**：当场标记 `error` 并写明原因，**不消耗重试次数**
- **为什么要提前拦**：超限文件上传必然失败，进队列只会把重试次数耗光

### L1.5 认领闸门：远端已有同名同大小的文件

- **判据**（两条**同时**成立）：
  - 文件名按**相对路径**匹配，不是 basename（否则 `a/x.jpg` 与 `b/x.jpg` 会误判成同一个）
  - 大小相等
- **命中**：直接认领为「已同步」，**整段读盘都省掉**（不用算哈希）
- ⚠️ **只对「从未同步过」的文件生效**（清单 `synced_size` 为空）。已同步过的文件若内容变了但大小不变，尺寸匹配会误判 → 漏传 → 备份缺口。那种情况必须走 L2。

### L2 哈希判重：远端已有相同内容

- **判据**：算出的 MD5 与清单里记录的远端哈希 `synced_md5` 相同
- **命中**：不上行，把 L1 基准刷新成当前值，下轮直接走 L1 这条更快的路

### 真实上传：Transfer

只有四道闸门都没拦下，才真正上行。

- **双哈希是硬性要求**：夸克秒传需要 **MD5 + SHA1 同时提供**，缺任一个服务端会整文件缓存（失秒传 + OOM 风险）
- **模式分流**：文件 > `singlePutMaxBytes` 时优先走分片，但要先探测服务端是否真有 `/multipart` 路由——部分实例会把该请求落到 SPA 的 index.html 上（HTTP 200 实则无此路由）

## 四、差异处置

对账产出的差异只有四类，**只回答「这个文件在不在」**：

| 差异 | 含义 | 默认动作 |
|---|---|---|
| `missing_remote` | 本地清单标为已同步，但远端不存在 | 自动重传 |
| `size_mismatch` | 两侧都有但大小不同 | 自动覆盖远端（本地为准） |
| `remote_only` | 远端有，本地无 | **只记录，不动作** |
| `local_only` | 本地有，远端无 | 尚未上传 |

**「仅修改时间不同」不算差异。** 复制、解压、跨设备同步都会改 mtime，而内容可能一模一样。把它列进清单只会制造噪声。

`remote_only` 默认只记录不动作，是为了避免误删其他设备刚上传的内容。

### 冲突策略

| 配置 | 行为 |
|---|---|
| `local-wins`（默认） | 自动用本地版本覆盖远端 |
| `manual` | 只记录，全部交由用户确认 |

自动修复有次数上限（`autoFixLimit`，默认 20）。超出后其余差异仅记录。

## 五、删除语义

**三个列表的「删除」含义完全不同，别删错地方：**

| 位置 | 删掉的是 | 远端会怎样 |
|---|---|---|
| 文件清单 | **本地文件** | 按删除策略跟进 |
| 传输队列 | **只是界面上的任务记录** | 不动任何文件 |
| 远端对账 | **远端文件** | 移入远端回收站，并关闭该差异 |

**删除策略**（连接与设置 → 删除策略）：

| 策略 | 远端行为 |
|---|---|
| 移入回收站（默认） | 远端文件移到 `_trash/<时间戳>/`，可恢复 |
| 直接删除 | 远端文件被物理删除，不可恢复 |
| 保留 | 远端文件不动，只把差异标记为已处置 |

在文件清单页删本地文件，等价于在资源管理器里删文件：远端会按删除策略跟进，不会出现「本地没了远端还在、下次又被拉回来」。

**改远端根目录不会搬动旧目录里的文件**，也不会重传一遍——清单里的远端路径会被改写成新根，旧根下的文件保持原样。

## 六、可信度：弱认定与强认定

清单里的 `verify_level` 回答「这条『已同步』的结论有多可靠」：

| 值 | 含义 | 怎么来的 |
|---|---|---|
| `hash` | 内容经哈希确认 | 真实上传、或 L2 哈希判重命中 |
| `size` | **仅凭同名同大小弱认定** | L1.5 认领闸门命中的那条路 |
| `null` | 未标记 | 从未同步过 |

**弱认定是真实的备份缺口**：同名同大小、内容其实不同的两个文件，会被认成同一个。补救手段是「深度校验」——把远端文件拉回来重算哈希做字节级比对（受 `verifyHashMaxBytes` 限制，默认 64MB，因为那是全量下行流量）。

清单页的「可信度」筛选就是用来把这些弱认定的文件捞出来的。

## 七、状态机

### 文件状态（`files.state`）

```
pending ──▶ hashing ──▶ hashed ──▶ uploading ──▶ synced
   │           │                      │            │
   │           └──▶ stale（内容已变）  │            │
   │                                  ▼            ▼
   └──────────────────────────────▶ error ◀───────┘
                    （重试耗尽，需人工处理）

deleted   本地已删除（远端按删除策略处理）
local_only / remote_only / conflict   对账差异态
```

### 传输任务状态（`TransferTask.state`）

```
queued ──▶ hashing ──▶ uploading ──▶ done
   │           │            │
   │           └──▶ skipped（判定结论，不是失败）
   ▼           ▼            ▼
canceled    failed ◀────────┘
```

**取消守卫**：任务一旦进入 `canceled`，任何非 `canceled` 的状态都不许写回去。取消按钮要是在「哈希算完了」那一刻点，界面不能又跳回「上传中」。

唯一的例外是**重试**——重试是用户主动要求再跑一次，它必须能把状态从 `canceled` 拉回 `queued`。

## 八、并发与去重

| 项 | 默认 | 说明 |
|---|---|---|
| `hashConcurrency` | 2 | 同时算几个文件的哈希 |
| `uploadConcurrency` | 2 | 同时传几个文件 |
| `singlePutMaxBytes` | 8MB | 超过此值优先走分片 |

**带宽瓶颈在 OpenList→夸克那一段（按账号共享限速），不在内网段。** 提高并发只招风控。

下载的并发单独限流，不与上传共用额度——下载不占上传的上行带宽，反过来也一样。

**去重的三个层次**：

1. **L1** — 清单基准（size + mtime）
2. **L1.5** — 远端目录缓存（同名 + 同大小），只对从未同步过的文件生效
3. **L2** — 内容哈希（`synced_md5`）

`enqueue()` 的去重**必须查在途项**（`inFlight`）：只看队列数组的话，正在 await 里的项会被排第二遍 → 远端出现 `xxx(1).ext`。

## 九、失败与恢复

### 重试

失败后按指数退避重试（`retry.maxAttempts`，默认 3 次）。**确定性失败不消耗重试次数**——例如超限文件，重试多少次都一样。

### 应用重启后的恢复

`recoverPending()` 把状态为 `uploading / error / hashed / pending` 的文件重新排队。

两个必须知道的点：

1. **清单表是全局的，不按 syncRoot 隔离。** 恢复前必须确认本地文件**确实存在**，否则换过同步目录后旧记录会被当成新文件重传，远端凭空多出目录。
2. **复用清单里的哈希前必须校验文件还是那个版本。** 哈希是上次的残留值；应用关闭期间用户改了文件，照抄旧哈希就等于对着一份新内容声明旧哈希——而夸克驱动正是拿双哈希做秒传判断的，结果是远端留着旧内容、本地是新内容。

### 退出

引擎退出时先停 Planner（不等在途任务）再关数据库。在途任务的写回会被数据库的关闭守卫拦下，不会把主进程带崩。

## 十、关键设计取舍

### 为什么 OpenList 的目录列表要带 `refresh`

OpenList 的目录列表是**快照缓存**。不带 `refresh: true` 的话，move 之后缓存里可能**仍然留着源文件** → 等待消失的逻辑永远判定「还在」→ 白等 20 秒 → 返回 false。

而如果 `move` 不检查这个返回值，false 就被当成成功——用户看到「已删除」，远端文件却好好躺着。

### 为什么远端删除要先等文件消失

删除流程是：move 到回收站 → 等源文件从列表里消失 → 才算成功。等不到就抛错，**绝不静默成功**。

### 为什么下载先写临时文件

下载直接写最终路径的话，中断时留下半截文件。它躺在同步根里，watcher 当成新文件 → 上传 → 带 Overwrite → **远端完好的那份被半截内容覆盖**。备份被自己搞坏了。

所以下载写 `.part` 临时文件，成功后才 rename。

### 为什么配置用函数而不是快照

配置可以在运行时改。如果 Transfer / Reconciler 持有构造那一刻的对象引用，用户在 UI 里改了「单文件上限」「回收站目录」「校验模式」，Planner 用新值、Transfer 用旧值——两边对「这个文件能不能传」给出相反的判断。

## 十一、界面该怎么看

| 页面 | 回答什么问题 |
|---|---|
| 概览 | 现在在忙什么？队列里有多少？当前速率多快？远端对账有没有在跑？ |
| 文件清单 | 每个文件的同步状态、可信度、对账差异分别是什么 |
| 传输队列 | 现在正在传什么？能不能取消/重试？跳过的是哪些、为什么？ |
| 远端对账 | 两侧有哪些不一致？该怎么处理？ |
| 运行日志 | 刚才到底做了什么？（按类别筛：上传/下载/跳过/对账/系统） |

**清单页的三组筛选是叠加的**：同步状态 × 对账差异 × 可信度。点「清除筛选」一键复位。

**队列页的两组筛选也是叠加的**：传输类别（上传/下载/跳过）× 任务状态（含「已完成」）。所以「只看已完成的下载」= 类别选「下载」+ 状态选「已完成」。

**跳过项不显示进度条**：跳过没有「进度」这回事——它根本没传。画一条空的进度条加「0%」，用户看到的是「卡在 0% 不动」，会反复点、或者以为程序坏了。那一列改成显示跳过原因（本地未变 / 远端已有 / 远端同名同大小 / 本地文件已不存在）。

**列表默认降序**：最新的排前面。用户找刚出问题的任务时，不用从几千条里往上翻。

**全选在表头**：以前全选框藏在底部批量条里，而批量条在「没选中任何项」时整个不渲染——用户永远看不到全选框，必须先手动勾一个才能全选。逻辑倒置。现在表头常驻一个全选框，勾上即选中当前筛选出的全部。

**两条通道各有各的进度条**：本地扫描和远端对账可以同时在跑，合并成一条的话一条的进度会把另一条顶掉。

## 十二、已知限制

1. **夸克侧拿不到秒传信号**：实测 PUT 响应恒为 `{"code":200,"data":null}`，驱动的 `hash_info` / `hashinfo` 都是 null。「远端重复」只能客户端自算。
2. **「远端重复」的比对基准是 `synced_md5`/`synced_sha1`**（远端已存版本的哈希），不能比 `md5`/`sha1`（本地当前状态）——后者一次失败的上传就会改写它。
3. **深度校验受 `verifyHashMaxBytes` 限制**（默认 64MB）。更大的文件只能退化到大小校验。
4. **分片上传的 `chunkConcurrency` 配置项尚未接线**，单文件分片目前是串行的。
5. **重命名识别依赖 inode 与时间窗口**（默认 5000ms）。跨磁盘移动或大文件会超出窗口，退化为「删旧 + 传新」。
6. **文件清单按需分页**：本地六万文件时每次只加载五千条，底部有「加载更多」按钮。清单里到底有多少条，看概览页的统计（那里做的是全表 COUNT）。
7. **虚拟滚动后 Ctrl+F 只能找到已渲染的行**。这是性能与浏览器原生查找之间的取舍——能滚动比能全文查找重要得多。
8. **同步根是盘符根（`Z:\`）时压力很大**：整块盘的每个目录都要占一个监控句柄，而且扫描要遍历全盘。网络映射盘/挂载盘的句柄承受力更低，实测 5.8 万个文件时驱动器会报 `EMFILE`，需要等它缓过来。程序会就此提示一句，但**建议同步根填具体的子目录**。
9. **本地盘句柄耗尽时会自动冷却重试，不判失败**。盘彻底断开时（重试 40 次仍拿不到句柄）才会停下，日志里会说明原因，恢复后重新扫描即可。
