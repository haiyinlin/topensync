# TopenSync

Windows 桌面同步程序：**本地目录 →（内网 HTTP）→ OpenList →（外网）→ 夸克网盘**。

远端保持**原始文件树**，在 OpenList 里可直接浏览、预览、播放。

仓库地址：https://github.com/haiyinlin/topensync

---

## 启动后默认不开始

程序打开后**不会**自动扫描、自动对账、自动上传——顶栏显示「开始同步」，
点它才启动本地监控、远端对账与上传队列。

理由：备份工具多半是开机自启的，用户可能只是路过看一眼状态。
启动瞬间就扫全盘、列远端树、抢带宽，不是用户想要的。

「扫描本地」「对账远端」两个按钮仍然随时可用——手动点了就等于开始同步。

## 这是什么

一个只做一件事的备份工具：把指定的本地文件夹单向同步到自部署 OpenList 暴露的夸克网盘存储。

设计上刻意保持克制：

- **单向同步**（本地为准）。远端对账只做校正，不把远端内容拉回本地。
- **不打包**。小文件逐个直传，保留完整目录层级。
- **不绕过服务端**。全部走 OpenList 的标准 HTTP 接口。

## 两条扫描通道

这是本项目最核心的概念，两者角色不同、不可互相替代：

| | 本地扫描 | 远端对账 |
|---|---|---|
| 性质 | 变更事件源 | 对账基准 |
| 触发 | 实时（整树单句柄监听）+ 兜底比对 | 定时（默认 6 小时）+ 手动 |
| 覆盖 | 本地同步根目录 | 远端根目录 |
| 发现 | 「本地改了」 | 「远端被外部删了 / 改了 / 多了」 |
| 动作 | 直接进上传队列 | 产出差异 → 差异回流进同一个上传队列 |

**为什么必须有远端对账**：只扫本地有一个静默漏洞——你在 OpenList 网页端删了某个文件，本地 mtime 没变，清单就认为它已同步，于是永远不再上传，备份就此缺失。对账周期性地重列远端树来发现这类偏差。

### 本地监控怎么工作

Windows 上一次 `ReadDirectoryChangesW` 就能监视**整棵子树**（`bWatchSubtree = TRUE`），
Node 把它暴露成 `fs.watch(root, { recursive: true })`——**整块盘也只占一个句柄**。
所以同步根设成整块盘（`Z:/`）是可行的，不需要为每个目录各开一个 watch。

代价是这个缓冲只有几十 KB，**突发大量变更会被系统丢弃**（不报错、不重发）：
实测本地 NTFS 上 1500 个文件 / 0.57 秒只收到 1 条事件。所以实时监听之外还有两道兜底：

1. **突发检测**：一秒内超过 120 条事件就判定为批量拷贝，安静后补一轮比对；
2. **周期全树比对**：`watchSafetyScanMinutes`（默认 30 分钟）遍历磁盘，按 `size + mtime`
   与上一轮比对，只把真正变化的文件交给上层。

也就是说：日常改一个文件是秒级同步；拷一整个目录进来时，**最多**等一轮兜底比对补齐。
把同步根缩小到子目录并不会更快，但能降低兜底比对的开销（全树 stat 在 SMB 上约 200 文件/秒）。

**两条通道不会互相打架**：手动点「立即对账」时，若上传队列还没跑完，对账会等它排空再开始。否则清单里还没记上刚传完的文件，对账会把它们误判成「仅远端存在」——那是假差异，照着界面提示去处理反而会误删远端文件。

差异处置默认立场是「本地为准」：

| 差异 | 默认动作 |
|---|---|
| 远端缺失 | 自动重传 |
| 内容不符 | 自动覆盖远端 |
| 仅远端存在 | **只记录，不动作**（避免误删其他设备刚上传的内容） |
| 时间差异 | 只记录 |

## 删除与批量删除

三个列表都支持「删除」和「批量删除」，但**三处的「删除」含义完全不同**，别删错地方：

| 位置 | 删掉的是 | 远端会怎样 |
|---|---|---|
| 文件清单 | **本地文件** | 按删除策略跟进（见下） |
| 传输队列 | **只是界面上的任务记录** | 不动任何文件 |
| 远端对账 | **远端文件** | 移入远端回收站，并关闭该差异 |

所有删除都会先弹二次确认，确认框里写明会删什么。

**删除策略**（连接与设置 → 删除策略）：

| 策略 | 远端行为 |
|---|---|
| 移入回收站（默认） | 远端文件移到 `_trash/<时间戳>/`，可恢复 |
| 直接删除 | 远端文件被物理删除，不可恢复 |
| 保留 | 远端文件不动，只把差异标记为已处置 |

**在文件清单页删本地文件**，等价于在资源管理器里删文件：远端会按删除策略同步跟进，不会出现「本地没了远端还在、下次又被拉回来」的情况。

**改远端根目录不会搬动旧目录里的文件**，也不会重传一遍——清单里的远端路径会被改写成新根，旧根下的文件保持原样，需要的话自己迁移。

## 技术栈

| 层 | 选型 |
|---|---|
| 框架 | Electron + electron-vite |
| 语言 | TypeScript（严格模式） |
| UI | React + Zustand |
| 监控 | `fs.watch(recursive)` 整树单句柄（Windows）；chokidar 作回退 |
| HTTP | Node 内置 `fetch`（undici），流式上传 |
| 清单 | `node:sqlite`（Node 22+ 内置，**无 native 编译**） |
| 哈希 | Node `crypto`（MD5 + SHA1 双哈希） |

**明确不用**：`webdav` 客户端库（写入路径不支持哈希头）、`better-sqlite3`（native）、zstd / tar（无归档需求）。

## 目录结构

```
src/
├── main/                  主进程
│   ├── index.ts           入口：单实例锁、窗口、引擎装配
│   ├── engine.ts          引擎：把四个模块装配成整机，对外暴露能力
│   ├── ipc.ts             IPC 通道注册（只转发，不含业务逻辑）
│   ├── config/store.ts    配置持久化（safeStorage 加密凭据）
│   ├── db/manifest.ts     SQLite 清单（node:sqlite）
│   ├── hash/hashes.ts     双哈希计算（MD5 + SHA1 一次读出）
│   ├── openlist/client.ts OpenList REST 客户端
│   ├── planner/           汇合点：L1 去重 + 哈希池 + 上传池 + 删除熔断
│   ├── reconcile/         远端对账器（remote_snapshot → diffs → 回流）
│   ├── transfer/          传输执行器（单次 PUT / 分片两档）
│   ├── verify/            深度校验（下载远端重算哈希）
│   ├── diagnostics/       诊断包导出
│   └── watcher/           本地监控（整树单句柄监听 / chokidar / 定时比对）
├── preload/               预加载（最小 API 面）
├── renderer/              渲染进程（React + Zustand）
└── shared/types.ts        主/预/渲染共享的类型定义

docs/                     业务流程与技术架构文档
├── BUSINESS-FLOW.md       业务流程：决策链、差异处置、状态机、设计取舍
└── ARCHITECTURE.md        技术架构：模块分工、路径约定、构建约束、验证脚本

resources/                应用图标（icon.ico 为打包用多尺寸图标）
scripts/                  实机验证脚本
tests/                    单元测试
ui-prototype/             静态视觉基准（浏览器可直接打开）
```

**四个进程内模块的分工**：

| 模块 | 职责 | 不做什么 |
|---|---|---|
| **Watcher** | 监听本地目录，产出归一化事件（add/change/unlink） | 不做上传决策，不碰远端 |
| **Reconciler** | 列举远端文件树 → 比对 → 产出差异 | 不回传内容到本地 |
| **Planner** | 两条通道的汇合点：去重决策 → 上传队列 → 删除队列 | 不直接发 HTTP |
| **Transfer** | 执行上传：哈希、双哈希头、单次 PUT / 分片 | 不做去重判断 |
